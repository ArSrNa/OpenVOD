部署方案：EdgeOne / 云函数 + 全栈一次性部署

含管理端与分发端技术栈最终建议 · 2026-09-17

先澄清三个最容易踩的概念错误
  1. EdgeOne 里有两个不同的"函数"，能力差别巨大。「边缘函数 / Edge Functions」基于 V8，只支持 JavaScript，CPU 时限 200ms；「Cloud Functions」跑在云服务器上，原生支持 Go 1.26，最长 120 秒。你说的"用 Go 部署到 EdgeOne"走的是后者。
  2. EdgeOne 还有两条产品线要分清。「边缘安全加速平台」（CDN / WAF / 边缘函数）和「EdgeOne Pages（Makers）」（全栈应用托管，含 Edge Functions + Cloud Functions + KV + 静态托管 + CI/CD）。要"一次性部署全栈"，你要用的是 EdgeOne Pages。
  3. SCF 镜像部署有一条会直接拦住你的限制：不支持 ARM 平台构建的镜像。SCF 是 x86 架构，你在这台 M4 上直接 docker build 出来的 arm64 镜像传不上去，必须 --platform linux/amd64 构建。

1. EdgeOne 的两套函数：Go 到底能不能用

维度Edge Functions（边缘函数）Cloud Functions（云函数）
运行位置EdgeOne 全球边缘节点云服务器（可选地域）
运行时V8 / Edge RuntimeNode.js 20.x · Python 3.10 · Go 1.26
Go 支持不支持（仅 JavaScript ES2023+）支持。Handler 模式（纯标准库，文件名即路由）／Framework 模式（Gin、Echo、Fiber、Chi），平台自动做框架检测、路由映射、交叉编译
CPU / 执行时间CPU 时间片 200ms（不含 I/O 等待）最长 120s（默认 30s，可配）
代码包≤ 5 MB≤ 128 MB（含依赖）
请求 body≤ 1 MB≤ 6 MB
冷启动毫秒级百毫秒级
数据访问可读写 Edge KV / Blob（全局变量方式）不能访问 KV
npm / 三方包不支持 npm 包与 Node 内置模块完整生态（Go Modules / npm / pip）
其他限制单站点 ≤100 个函数、≤200 条触发规则、循环 ≤100,000 次、console ≤20 次官方建议：需长期保留的数据用 COS，不要存在函数侧
适合什么请求预处理、鉴权转发、重定向、KV 读写的轻逻辑访问数据库、复杂 JSON、密钥解密——你的分发端主体
结论：Go 可以用，走 Cloud Functions。EdgeOne 对 Go 的支持相当完整（1.26、主流框架、自动交叉编译与路径映射），比 Node 更省配置。唯一要注意的是：边缘节点那一层（Edge Functions）只能用 JS，所以如果你想把某些逻辑压到最近的边缘节点（比如从 KV 读元数据、用 Web Crypto 签 URL），那部分必须用 JavaScript 写。

多地域部署

Cloud Functions 支持多地域，配置在 edgeone.json：

{
  "mainlandRegions": ["ap-shanghai"],
  "overseasRegions": ["ap-singapore"]
}

中国大陆可选：广州、上海、南京、北京、成都；海外可选：新加坡、中国香港、曼谷、雅加达、首尔、东京、法兰克福、弗吉尼亚、硅谷。每项数组只能填一个地域。你在上海，大陆地域选 ap-shanghai 能显著降低回源与数据库访问延迟。

2. SCF 云函数容器镜像部署的硬限制

你说的"Docker 到云函数"技术上成立，但门槛比想象中多。以下是官方明确的使用限制：

限制项值对方案的影响
CPU 架构 SCF 基于 x86，不支持在 ARM 平台（Apple M 系列）构建的镜像 M4 上必须 docker build --platform linux/amd64，不能直接本地 build 后推上去
镜像大小 解压前 ≤ 1 GB（可提工单申请提高） 转码镜像（含 ffmpeg + packager）极易超限，这基本封死了"转码上云函数"的路
镜像仓库 仅 腾讯云 TCR 企业版/个人版，且仅同地域私有仓库 镜像必须推到与函数同地域的仓库，跨地域构建流程要额外处理
监听端口 必须监听 0.0.0.0:9000 或 *:9000 镜像里的服务改端口；本地 compose 与云上要区分
启动时间 必须在 30 秒内完成启动 否则健康检查超时，报 The request timed out in 30000ms
执行超时 1–900 秒（默认 3 秒）；异步执行开启后最长 24 小时（创建后不可改） 默认 3 秒一定要改；长任务必须开异步执行
初始化超时 3–300 秒，镜像部署默认 90 秒 大镜像要调大，否则冷启动失败
容器可写层 512 MB 转码临时文件放不下，需挂 CFS
网络 支持 VPC 私有网络、固定出口 IP、挂载 CFS 文件系统 这是 SCF 相对 EdgeOne Cloud Functions 的最大优势：能直连 VPC 内的 TDSQL-C MySQL
冷启动优化 镜像加速（平均 5 倍）、预置并发、单实例多并发 分发端若上 SCF，建议开镜像加速 + 预置并发

3. 组件 → 部署目标映射

核心原则：不是所有组件都能上边缘。下面这张表是本次方案最关键的判断——选错部署目标会导致功能直接不可用。
组件能否上 EdgeOne能否上 SCF推荐部署目标原因
管理端 API + 后台 UI 可（Cloud Functions） 可（镜像） 常驻容器（轻量服务器 / CVM / CloudBase 云托管） 需要长连接、大文件直传签名、S3 操作、SSE 进度推送。放函数徒增复杂度无收益
转码 Worker 不能 不能 必须常驻容器 要 ffmpeg + packager、要临时磁盘（几十 GB）、要跑几分钟到几十分钟。SCF 镜像 ≤1GB、超时 900s、可写层 512MB，三条全部撞墙
分发端 API（元数据 + 播放清单 + 密钥） 可（Cloud Functions，Go） 可（镜像，Go） EdgeOne Cloud Functions 首选；需 VPC 直连内网 MySQL 时改 SCF 无状态、请求短（<200ms）、需全球低延迟。Cloud Functions 最长 120s 完全够用
边缘签名 / 鉴权转发 可（Edge Functions，JS） 不能 EdgeOne Edge Functions 毫秒级冷启动、可读 KV、可用 Web Crypto 做 HMAC——正好是签名所需的全部能力
数据库 不支持 — TDSQL-C MySQL（VPC 内网） 务必不要用公网暴露数据库
对象存储 + 视频分发 COS + EdgeOne CDN — COS 私有桶 + EdgeOne 加速域名 视频字节绝不能经过函数
元数据快照（可选） Edge KV 读不了 KV Edge KV（发布时同步写入） 让 Edge Functions 零回源取元数据。注意：密钥绝对不能放 KV

推荐的两种部署形态

形态 A：EdgeOne Pages 一体化（推荐，最接近"一次性全栈"）

vod-edgeone/ ├── edgeone.json # 地域、构建、路由配置 ├── src/ # 前端（React/Vite 或 Next.js） ├── edge-functions/ │ └── api/ │ ├── sign.ts # JS：从 KV 读快照 + Web Crypto 签 CDN URL │ └── geo.ts # JS：地域/风控转发 └── cloud-functions/ └── api/ ├── playback.go # Go：播放清单，缓存兜底 ├── keys.go # Go：AES-128 密钥下发（校验 token） └── assets.go # Go：媒体元数据

一次 edgeone pages deploy 或一次 git push，前端 + 边缘函数 + 云函数 + CDN + 域名全部上线。这是目前最贴合你"一次性部署全栈"诉求的方案。

形态 B：混合（分发端上 EdgeOne，管理端与转码在服务器）

COS（私有桶）
  ↑ 回源
EdgeOne（CDN + 签名/鉴权 + Edge Functions + Cloud Functions·Go）
  ↑ HTTP（内网或加签）
管理端 + 转码 Worker（轻量应用服务器 / CVM / CloudBase 云托管）
  ↑ 内网
TDSQL-C MySQL

形态 B 的分发端不直连数据库：元数据在发布时同步到 Edge KV，密钥端点经内网 HTTP 回调管理端的只读接口。好处是数据库完全不暴露、EdgeOne 侧无状态；代价是多一跳延迟，且需要一个稳定的内网通道（专线或对等连接）。

4. 一次性部署全栈：五种办法

先给一个诚实的判断：没有任何单一工具能"一条命令"把「容器化 Worker + 云函数分发端 + 边缘函数 + 数据库 + 对象存储 + CDN + 域名备案」全部部署完。数据库有独立生命周期，CDN 的地域/备案/证书需要人工环节，容器镜像构建必须先于函数创建。但可以做到"一条命令触发全链路"。

办法覆盖范围一次命令评价
EdgeOne Pages（Git 集成） 前端 + Edge Functions + Cloud Functions + CDN + 域名 edgeone pages deploy
或一次 git push		 全栈一体化程度最高。但覆盖不到自建容器与数据库，需与形态 B 配合
CloudBase 云开发 静态托管 + 云函数 + 云托管（容器）+ 云数据库 cloudbase framework deploy 腾讯生态内一体化最完整；云托管能放常驻容器，可以连"管理端 + 转码"一起搞定，是唯一能真正覆盖"全栈"的单平台
Terraform COS、CDN/EdgeOne、SCF、TDSQL-C、TCR、VPC、DNS 全覆盖 terraform apply 真正的 IaC，可重复可审计，适合生产。代价是要写不少 HCL，且镜像构建推 TCR 这一步 TF 做不了，必须前置
Serverless Framework
（serverless-tencent）		 SCF、API 网关、COS、CDN serverless deploy 比 TF 轻，但插件维护状态需自行确认；多云抽象层反而增加调试成本
GitHub Actions + Taskfile 编排以上所有 task deploy 最可控：把构建镜像 → 推 TCR → 部署 SCF → 迁移数据库 → 发布 EdgeOne Pages 串成一条流水线，每个环节都能单独重试
自托管 PaaS
Coolify / Dokploy / Kamal		 全栈 docker compose git push 或 kamal deploy 部署到自有服务器时最省心；但完全不覆盖 EdgeOne / 云函数路线

推荐落地方式：Taskfile + GitHub Actions 编排

# Taskfile.yml —— 一条 task deploy 触发全链路，每步可独立重试
version: '3'
tasks:
  deploy:
    cmds:
      - task: db:migrate            # 1) 数据库迁移（带版本与回滚点）
      - task: image:build           # 2) 构建 linux/amd64 镜像（关键：必须指定平台）
      - task: image:push            # 3) 推 TCR 同地域私有仓库
      - task: worker:rollout        # 4) 滚动更新常驻 Worker
      - task: admin:rollout         # 5) 滚动更新管理端
      - task: edgeone:deploy        # 6) 发布 EdgeOne Pages（前端+边缘+云函数）
      - task: smoke                 # 7) 冒烟：构建产物断言 + 端到端播放校验

  image:build:
    cmds:
      # 关键：SCF 是 x86，M4 上必须交叉构建，否则镜像传不上去
      - docker buildx build --platform linux/amd64
          -f docker/delivery.Dockerfile -t ${TCR}/vod-delivery:${GIT_SHA} .

  smoke:
    cmds:
      # P0 断言：密钥与播放路由必须是动态路由，不能被静态化
      - bash scripts/assert-dynamic-routes.sh
      # P0 断言：无签名请求必须 403
      - bash scripts/assert-unsigned-403.sh
把两条 P0 断言做成 CI 的硬门禁（对应上一版方案里的风险）：
  1. assert-dynamic-routes.sh：如果分发端是 Next.js，解析 next build 输出，要求 /api/keys/* 与 /api/playback/* 显示 ƒ Dynamic，出现 ○ Static 直接 fail。若分发端是 Go，则改为断言响应头含 Cache-Control: no-store。
  2. assert-unsigned-403.sh：对 CDN 域名发一个不带签名的 m3u8 请求，断言返回 403。
这两条一旦进 CI，"密钥被缓存"和"签名失效"这两个 P0 风险就被自动化挡住了。

5. 管理端与分发端技术栈（最终建议）

5.1 管理端 Control Plane

层选型理由
运行时Bun + Hono纯 IO 编排型负载（发签名、写库、调度任务），Bun 启动快、依赖少；Hono 轻量且能同时跑在容器与 CloudBase 云托管里
ORMDrizzle ORM + MySQL 8同一套 schema 可产出 MySQL / SQLite 方言，保留你"SQLite 或 MySQL"的切换余地；迁移工具内建
后台 UIReact + Vite + TanStack Query纯 SPA，不需要 SEO；构建产物交给 nginx 或 COS 静态托管
转码 Worker独立容器：Bun/Go + ffmpeg + packager与管理端同仓不同入口；镜像较大但只在常驻容器里用
任务队列MySQL 表 + FOR UPDATE SKIP LOCKED不引入 Redis，满足你的数据库约束
对象存储COS（S3 兼容接口）本地开发用 MinIO，生产用 COS，代码不变
部署轻量应用服务器 / CVM / CloudBase 云托管云托管可省掉容器编排，且与云函数同生态

5.2 分发端 Data Plane

层选型理由
语言 Go 1.26 EdgeOne Cloud Functions 原生支持 Go 1.26，含框架检测、路由映射、交叉编译自动化——比 Node 少配置。同时它也能以镜像形式部署到 SCF
框架 Chi（或 Echo / Gin / Fiber） EdgeOne 官方点名支持这四个；Chi 最贴近标准库、依赖最少，冷启动友好
边缘层 Edge Functions（JavaScript） Go 用不了这一层。仅用于：从 Edge KV 读元数据快照、Web Crypto 签 CDN URL、鉴权转发
数据访问 方案一：Edge KV 快照（只读，发布时同步）
方案二：VPC 直连 TDSQL-C（改用 SCF）
方案三：内网 HTTP 回调管理端只读接口		 三选一或组合。KV 最快但最终一致性 ≤60s；VPC 最方便但要把分发端放在 SCF；回调最安全
密钥下发 Go handler，Cache-Control: no-store 绝不进 KV、绝不进 CDN、绝不上边缘缓存
视频分发 COS 私有桶 + EdgeOne 加速域名 视频字节完全不经过函数；签名方案见上一份文档第 7 节
部署 EdgeOne Pages Cloud Functions（首选）
或 SCF Web 函数（需 VPC 时）		 前者一体化程度高、有海外节点；后者能连内网、可挂 CFS、异步最长 24h

5.3 一个必须处理的问题：monorepo 里的双语言契约

如果管理端用 TS、分发端用 Go，你上一版提到的"双语言模型漂移"风险又回来了。标准解法：

# 契约唯一真相源：packages/contracts 里的 zod schema
packages/contracts/src/
  ├── playback.ts      // export const PlaybackResponse = z.object({...})
  ├── publication.ts
  └── index.ts

# 生成步骤（CI 里跑，生成物提交入库）
bun run contracts:json     # zod → JSON Schema
bun run contracts:go       # JSON Schema → Go struct（用 quicktype 或 oapi-codegen）
                          # 输出到 apps/delivery-go/internal/contracts/

# CI 门禁：生成物与仓库内已提交的版本不一致就 fail
git diff --exit-code apps/delivery-go/internal/contracts/

关键点是把生成物提交入库并在 CI 里做 git diff --exit-code 校验。否则"生成了但没人跑"等于没做，漂移照样发生。

6. 限制与风险清单

限制 / 风险等级说明与应对
SCF 不支持 ARM 构建的镜像 P0 你在 M4 上必须 docker buildx build --platform linux/amd64。建议在 CI 里构建而不是本地，顺带解决一致性问题
转码不能上任何函数 P0 SCF 三条限制同时撞墙：镜像 ≤1GB、超时 900s、可写层 512MB。转码必须常驻容器 + 独立大磁盘
密钥绝不能进 Edge KV / CDN 缓存 P0 KV 会全球复制，边缘缓存会把密钥落到不受控节点。密钥端点必须回源，且 no-store + CI 断言
EdgeOne Cloud Functions 的数据库连通性 P1 官方文档未提供 VPC 打通说明，且明确建议持久化数据用 COS。上线前必须实测：Cloud Functions 能否连内网 TDSQL-C。连不通就走 Edge KV 快照 + 内网回调，或分发端改放 SCF
Edge Functions 的 200ms CPU 限制 P1 只放极轻逻辑。任何涉及多次网络往返或复杂计算的东西都要放到 Cloud Functions
Edge Functions 不支持 npm 包 P1 签名逻辑只能用 Web Crypto 手写，不能用现成的 SDK。HMAC-SHA256 手写约 30 行，可接受
中国大陆加速需域名备案 P1 这是流程性阻塞项，通常耗时数天到数周，应尽早启动而不是等开发完成
EdgeOne Cloud Functions 冷启动为百毫秒级 P1 播放首帧体验受影响。可接受，但密钥与清单端点应放在同一函数实例内减少冷启动次数
Cloud Functions 不能读 KV P1 Go 侧拿不到边缘 KV 的快照，两套数据源要么统一走 KV（那 Go 也得改成 JS），要么统一走 DB/HTTP
双语言契约漂移 P1 用 zod → JSON Schema → Go struct 的生成 + CI git diff --exit-code 门禁消除

7. 建议的落地顺序

  1. 先做连通性验证（1 天内）：在 EdgeOne Cloud Functions 里写一个最小 Go 函数，尝试连接你的 TDSQL-C（或任意内网 MySQL）。这一步的结果直接决定形态 A 还是形态 B，比写任何业务代码都优先。
  2. 同时启动域名备案：这是不可压缩的等待时间。
  3. 搭 EdgeOne Pages 项目骨架，跑通"前端 + 一个 Go Cloud Function"的部署闭环，确认 edgeone pages dev 本地调试体验符合预期。
  4. 再回到 M1–M3 的功能竖切（上传 → 探测 → 转码 → 加密 → 签名播放）。
  5. 最后把 Taskfile 与 CI 门禁补齐。
本页事实来源：EdgeOne 官方文档（Edge Functions 使用限制：代码包 5MB、body 1MB、CPU 200ms、开发语言目前仅支持 JavaScript ES2023+；Cloud Functions 支持 Node.js 20.x / Python 3.10 / Go 1.26，代码包 128MB、body 6MB、最长执行 120s、多地域可配、Cloud Functions 不能访问 KV、官方建议持久化用 COS；Go 运行时支持 Handler 与 Framework 双模式，框架检测/路由映射/交叉编译自动化）；腾讯云 SCF 官方文档（镜像部署：镜像解压前 ≤1GB、仅支持同地域 TCR 私有仓库、必须监听 9000 端口、须在 30 秒内启动、SCF 基于 x86，不支持 ARM 平台构建的镜像、可写层 512MB、执行超时 1–900s、异步执行最长 24h、初始化超时镜像默认 90s、支持 VPC / 固定出口 IP / CFS、镜像加速平均 5 倍）。EdgeOne CLI 命令与 edgeone.json 字段来自官方文档与公开技能说明。其余为架构设计建议。
