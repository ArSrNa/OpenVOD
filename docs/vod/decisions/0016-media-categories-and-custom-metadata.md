# ADR-0016：媒资分类、描述与标签（自定义元数据）

- 状态：已接受（2026-09-24，用户委托决策）
- 日期：2026-09-24
- 关联：ADR-0004（数据库与 ORM）、ADR-0005（存储布局）、ADR-0010（分发端 API 面）、intent.md「媒资分类与自定义元数据」、spec.md §8

## 背景

intent 新增需求（2026-09-24 用户定）：

- 媒资管理要能**设置分类、描述、标签**，且这三项要**在自定义元数据里体现**；
- **分类管理是一个独立模块**，分类**层级不限**（无限层级）；
- 因此需要决定：分类的存储形态（表 / JSON）、层级表达（邻接表 / 路径物化 / 嵌套集）、
  标签是否实体化、自定义元数据（`media.custom_data`）与这三项的关系，以及分发端如何输出（ADR-0004 的「公开白名单」一直未定义）。

既有事实：`media.custom_data`（JSON）在 M1 就存在于 schema 与 Go 读模型里，但**没有写入口**，
分发端 `custom` 恒为空对象（spec.md §6.6 遗留项）。

## 决策

### 1. 分类：独立表 `media_categories`，无限层级邻接表

- 字段：`id`（cuid）、`name`、`description`、`parent_id`（自关联，可空 = 顶级）、
  `sort_order`（同级排序）、时间戳；
- **层级不限**：以 `parent_id` 邻接表表达（不做路径物化 / 嵌套集）；树由应用层组装
  （管理端 `lib/category-tree.ts`，两层缓存：无）；
- **同级不允许重名**：DB 唯一索引 `(parent_id, name)` 覆盖非顶级；
  `parent_id IS NULL` 在 MySQL / SQLite 中互不相等，故顶级重名由**应用层同级查询**兜底；
- **环路禁止**：移动分类时校验「目标上级不得是自身或自身子孙」（应用层，DB 无法表达）；
  递归函数一律带 visited 集合，脏数据也不会无限递归；
- **删除语义**：有子分类 → 409（先删 / 先移走）；删除分类**不删媒资**，该分类下的媒资**迁入默认分类「其他」**
  （2026-09-24 同日修订，见下方补充：不再有「未分类」终态；DB 层 `ON DELETE SetNull` 仅作兜底）；
- 管理端**独立模块**：侧边栏「分类管理」（`/categories`）+ `/api/admin/categories*`，
  不塞进媒资列表的行内操作。

### 2. 描述与标签：媒资自身字段

- `media.description`（`String?`，VARCHAR(191)）与 `media.tags`（`Json?`，字符串数组）；
- **标签不做实体化**：v1 标签是媒资上的字符串数组（≤20 个 / 每个 ≤32 字符，服务端 trim + 去重），
  不建标签表、不做跨媒资标签治理（重命名 / 合并 / 标签云）——那是独立的治理型需求；
- 媒资对分类是**外键引用**（`media.category_id`，可空），不是 JSON 里塞 id。

### 3. 自定义元数据 = 三项的**稀疏投影**（`custom_data` + `custom.json`）

- `media.custom_data` 的语义**收敛为**自定义元数据的投影载体：

  ```json
  {
    "category":    { "id": "…", "name": "科幻", "path": "电影 / 科幻" },
    "description": "简介文本",
    "tags":        ["4K", "科幻"]
  }
  ```

  **空项不出现**（无分类 / 空描述 / 空标签数组一律省略键）；
- **写入时机**：管理端每次保存分类 / 描述 / 标签时重算（`mergeCustomData`），
  保留白名单之外的扩展键（历史或手工写入的键不被抹掉）；
- **导出**：同时写 `metadata/{id}/custom.json`（与投影同内容，`metadata/` 分区的业务扩展元数据对象，
  幂等覆盖）。导出是**投影副本**：失败只告警、不回滚 DB（DB 为准，下一次保存补齐）；
- **分类改名 / 移动 → 刷新投影**：投影里的 `name` / `path` 是快照，分类结构变化后由管理端
  同步刷新受影响媒资（该分类子树下全部媒资）的投影与导出对象。v1 同步逐条执行。

### 4. 分发端：公开白名单（ADR-0004 遗留项收口）

- 分发端**不查分类表**（受限账号无该表授权），只读 `media.custom_data` 并按**公开白名单**输出
  `custom` 对象：`category` / `description` / `tags` 三个键，其余键一律丢弃；
- 白名单解析在 Go 侧 `internal/server/custom.go`（键名与 `@openvod/shared MEDIA_CUSTOM_KEYS` 手工对齐，
  同 token 类型 / 设置的机制）；类型不符 / 脏 JSON → 空对象（播放链路不因元数据中断）；
- 同一份白名单同时作用于 `GET /v1/media` 列表项与 `GET /v1/media/{id}` 详情；
- 投影里的分类含 `name` / `path` 快照，是分发端「零 join」输出分类信息的**前提**。

### 5. 管理端 API 语义

- 自定义元数据设置复用 `PATCH /api/admin/media/{id}`（部分字段更新）：
  `title`（重命名语义不变）、`description`、`tags`、`category_id`（`null` = 清空 / 移出分类）；
- 读取侧 `GET /api/admin/media/{id}` 返回 **`custom` 恒三项**（`null` / `null` / `[]` 表示空，
  便于表单回填），另附 `customData` 投影原文（稀疏）；
- 敏感操作审计：`media.metadata_update`、`category.create` / `category.update` / `category.delete`。

### 补充（2026-09-24 同日修订）：默认分类「其他」

用户追加要求：**没设置分类的情况下，默认分类是「其他」**。落地为**系统内置分类**，而不是展示层占位文案：

- `media_categories.is_system = true` 的一条顶级分类「其他」（固定 id `cother00000000000000000`，
  即 `@openvod/shared MEDIA_DEFAULT_CATEGORY_ID`，符合分类 ID 形状白名单），**不可删除**（409）；
  默认 `sort_order = 10000`（排在顶级末尾），改名 / 移动 / 排序可改（id 不变，投影跟着刷新）；
- **「未设置分类」不再是合法终态**，三条路径保证：
  1. **上传**新媒资即落 `category_id` 与 `custom_data` 投影（新媒资不留空）；
  2. `PATCH /api/admin/media/{id}` 的 `category_id: null`（移出分类）等同**归入「其他」**；
  3. 读取路径对历史 `NULL` 仍**回退**为「其他」（`pickCategoryRef`：显式 id → 缺省 → 默认分类）；
- **删除其它分类**：该分类下的媒资**迁入**「其他」（`updateMany`，不再留 NULL），再删分类并刷新投影；
- **默认分类改名 / 移动**：未设置分类的历史媒资（`category_id IS NULL`）一并刷新投影（语义上它们归属「其他」）；
- **幂等确保存在**：MySQL 由两条迁移保证（`20260924130000_default_category` 插入默认分类 +
  `20260924140000_backfill_default_category` 回填历史行的 `category_id` 与投影）；SQLite（`db push`，无种子）
  与任何缺口由读取路径 `ensureDefaultCategory()` 幂等补建（主键固定 → 并发安全）；
- `media_count` 口径：未设置分类的历史媒资计入「其他」；
- 分发端由此**零改动**：投影里的 `category` 恒存在，「其他」与普通分类在下发形态上无区别。

**备选（否决）**：在管理端 / 分发端做展示层占位（`category` 缺省时前端显示「其他」）—— 否决：
同一语义出现两种下发形态，且分发端要硬编码中文名；内置分类让投影、白名单、同级判重、
`media_count` 全部沿用既有机制，代价只是多一条系统行。

## 理由

- **分类是"树实体"**：需要层级、排序、重命名即时生效与「按分类找媒资」，JSON 内的路径字符串无法承担
  （改名要么逐媒资重写、要么读到陈旧值），故必须独立表 + 外键；
- **描述 / 标签是"媒资属性"**：单值 / 小数组，随媒资读写，用列最省事；标签实体化会引入
  标签表 + 关联表 + 治理 API，超出本次需求；
- **投影而非读时组装**：分发端受限账号只被授权约定表（ADR-0011），投影让 `custom` 输出零新增授权、
  零 join，也把"哪些字段可以给播放端看"收口到管理端的一处写入逻辑；
- **白名单收口遗留项**：ADR-0004 的「公开白名单输出」在 M3 一直空着（§6.6），
  本次以三个已登记的公开字段实现，语义与「自定义元数据」完全一致。

## 备选（否决 / 搁置）

- **分类只存 `custom_data.category`（JSON 内路径字符串）**：改名 / 移动要批量重写全部媒资的 JSON，
  且「分类列表」无法从 JSON 里可靠重建 —— 否决；
- **分类路径物化列**（`path` / `path_ids` / 深度）：查询与展示更快，但移动子树要重写整棵子树的行，
  一致性与事务成本高（v1 分类规模小，应用层算路径足够）—— 搁置（演进项）；
- **标签独立表 + 关联表（标签库）**：支持标签治理与统计，但引入两张表与全部标签 API，
  与「v1 只做设置」不匹配 —— 搁置（演进项）；
- **分发端直连 `media_categories` 做 join**：白名单注释里需要最新分类名，代价是给受限账号多授一张表、
  且分类改名会立刻改变已签发 token 的输出 —— 否决（用投影快照，改名时管理端刷新）；
- **读时组装 `custom`（不落 `custom_data`）**：DB 层没有单一投影，`custom.json` 导出物与
  `custom_data` 列都会失去意义，且分发端要 join —— 否决。

## 后果与风险

- **双写与刷新成本**：`custom_data` 是投影，分类结构变化时要刷新受影响媒资（同步逐条）。
  分类规模 / 单分类媒资数量很大时，保存分类会变慢 → 演进为异步任务（已在 spec.md §8.3 标注）；
- **`description` 上限 191 字符**：对齐 Prisma `String` 在 MySQL 的 VARCHAR(191)（双方言 schema 逐字一致，
  不能引入 `@db.Text` 单方言属性）。需要长文本时按 ADR-0004 的双方言纪律另立决策；
- **同级重名的顶级例外**：顶级分类的重名只能靠应用层拦截（NULL 唯一索引语义），
  并发创建理论上可绕过（v1 管理端单管理员操作，接受）；
- **标签无治理**：改名 = 逐媒资改，跨媒资统计要扫 JSON（SQLite 下为 TEXT）—— 演进项；
- **深树 UI 成本**：树表 / TreeSelect 一次渲染全部分类，数千节点时需要懒加载 —— 演进项；
- **默认分类是「数据」而非常量**：它可被改名 / 移动 / 排序，因此消费方**不得**按名字或 id 做业务判断
  （唯一用途是「未设置时的归属」与「删除保护」）；判重靠同级唯一约束，删除保护靠 `is_system`。
